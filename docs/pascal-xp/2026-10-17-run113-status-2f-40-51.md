Source: `pascal-xp-focused-analysis-113.zip` (run 39055673968, commit `c8828f8ddf8e238ab4837d09864f24adfe5df79d`), extracted `win7_fecs_helper_callers.json` and `xp_fecs_helper_callers.json`. Read-only static decompilation; no driver changes, no claim of GP106 runtime evidence.

## Verified Win7 entry path

`FUN_001A88E8` (2414 bytes):

1. `FUN_001C54F4()` preflight; true => immediate `return false` (semantic of guard unresolved).
2. `FUN_00234AB8(param_1)`, nonzero => return false.
3. `FUN_001CAE88(deviceId)`, nonzero => log diagnostic `0x6E10000`, failure.
4. `FUN_001C8700(&slot)`, nonzero => log `0x6EA0000`, failure.
5. `FUN_001C50F0(slot)`, nonzero => log `0x6F30000`, failure.
6. `thunk_FUN_0021BBF8(...)`, nonzero => log `0x6FD0000` and call `FUN_001C52A4(slot)`.
7. `FUN_001C5408(1U << slot)`, nonzero => log `0x7250000` and call `FUN_001C52A4(slot)` (but callee always returns zero in decompiled body).
8. `FUN_001C8754(slot, gpuParams)`, nonzero => log `0x73C0000` and call `FUN_001C52A4(slot)`.
9. Only now proceeds to post-GPU-init work and returns success if no later errors.

The function's result is `iVar5 == 0`: it is a boolean, not a numeric propagation of NV_STATUS to its caller. Diagnostic constants are logging identifiers, NOT the returned statuses (`0x2F`, `0x40`, `0x51`).

## `FUN_001C50F0(uint slot)` (436 bytes)

- `slot > 31` => asserts via `FUN_00199394(0,1)`, returns `0x1F`.
- `mask = 1U << slot`; when `DAT_007E4588 & mask` is nonzero => asserts and returns `0x40` (slot is already reserved).
- Calls `FUN_001BF888(&DAT_007DACB0 + slot*8)`; nonzero status propagates verbatim.
- Zeros the 24-byte slot record at `DAT_007E4598 + slot*0x18`, calls `FUN_001BB984(0,1)` and stores the returned pointer into the record. Null pointer => `0x51` and cleanup; this strongly suggests allocation/obtain-context failure but the callee body is not analyzed here.
- Non-null => populates fields, then `FUN_001C4860(DAT_007E4588,0,returnAddress)`; if nonzero, propagates the returned status and cleans up.
- On success only: sets occupancy bit `DAT_007E4588 |= mask`, updates max occupied index `DAT_007E4594`, writes ring-buffer diagnostic and calls `FUN_001C4AF4(oldMask,0,0,returnAddress)` before returning zero.

Important: `DAT_007E4588` is the slot-occupancy bitmap; not to be confused with the activation bitmap below.

## `FUN_001C5408(uint64 mask)` (110 bytes)

- Initializes iterator storage, calls `FUN_001C9D40(mask,iterator)` until it returns null.
- For every returned GPU object `lVar2`, calls its method at `*(*(lVar2 + 0x1E28) + 0x418)` with `(lVar2, *(lVar2+0x1E28), 0)`.
- If that virtual method returns nonzero => `FUN_00199394(0,1)` assertion; **no error return**.
- Atomically ORs `DAT_007E458C |= (uint)mask` and returns **zero**.
- `DAT_007E458C` is the activated-GPU bitmask, distinct from occupancy `DAT_007E4588`.
- Consequently `0x7250000` logging in caller is syntactically present but has no nonzero return path through `001C5408` in the available decompilation. The assert and GPU method can have side effects; return-zero alone does not prove harmless behavior.

## `FUN_001C8754(slot, GPU params)` (567 bytes)

- Calls `FUN_001C4EA4()` *before* the root registry method `root + 0x90` for resource `0x7EF3CB`.
- If its first result is false, calls predicate a second time (apparently for assertion verification), optionally asserts via `FUN_00199394(0,1)`, and unconditionally returns `0x2F`. The second call is not a retry that changes the return code.
- If predicate is true, executes root `+0x90`, obtains GPU via root `+0x188`, performs initial preparation and then success-dependent operations `FUN_0019F478`, `FUN_001A95A8`, `FUN_001A93D4`, GPU virtual `+0x90`.
- First such failure is propagated to caller and can trigger diagnostic `0x73C0000`; thus the diagnostic does NOT uniquely identify status `0x2F`.
- `FUN_001C4EA4` body is not in artifact. It appears in 207 Win7 decompiled function bodies; paired lock acquire/release implementations `FUN_001C4D90`/`FUN_001C4EC8` are consistent with it being a generic RM lock/context predicate, not GPU architecture selector. This is an inference, not proof.
- XP counterpart `FUN_0009E0C0` has same root resource query and GPU virtual init structure but lacks the explicit predicate preflight.

## Possible chaining / cleanup

On nonzero return from `001C8754`, `FUN_001A88E8` logs `0x73C0000` and calls `FUN_001C52A4(slot)`.
`FUN_001C52A4` clears the occupancy bit **only if** its call to `FUN_001C4860(...)` returns zero. Otherwise it skips the clear. Accordingly, if cleanup itself fails, the slot may remain reserved; a later attempt could hit `001C50F0 -> 0x40`. This is a static **conditional scenario**, not evidence that it happens on GP106 hardware. No demonstrated link connects `0x2F` to `0x40` or `0x51` at runtime.

## Decision and interpretation

- Confirmed pre-root-resource-query blocking points: `001C50F0` (`0x1F`, `0x40`, `0x51` and propagated helper statuses), and `001C8754` first `FUN_001C4EA4()` (`0x2F`). Also outer callers can fail before these functions.
- `001C5408` by itself cannot propagate nonzero status in its decompiled body; virtual callback failure only asserts. Its side effects or assert could still affect later initialization.
- This establishes ordering relative to the `root+0x90` lookup of resource `0x7EF3CB`, **not** the exact location of GP106 PCI/device-class selection, which remains unproven.
- The likely diagnostic discriminator is event `0x6F30000` for slot-prep failure versus `0x73C0000` for GPU-init failure; runtime inspection of `iVar5` is needed to distinguish individual numeric statuses.
- No change to GitHub repository, firmware, or drivers is warranted by these static findings.
